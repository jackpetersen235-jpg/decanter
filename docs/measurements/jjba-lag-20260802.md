# JJBA "lag" 2026-08-02 — RESOLVED: the TV, not the Mac

Raw telemetry: `jjba-lag-20260802.log` (600 samples, ~2s apart, menu + live match).

**Cause: audio output was routed to an AirPlay device ("GREAT ROOM" — a TV).**
Confirmed by the user after the session. Nothing on the Mac was at fault.

## Why it looked like a performance problem
The complaint was "lag", and lag is assumed to be framerate. It wasn't — AirPlay
audio buffers ~1-2s by design, so every hit and input cue lands late and the whole
game *feels* delayed while rendering fine.

## Ruled out, with numbers — check these before suspecting Wine/DXMT again
| Suspect | Evidence |
|---|---|
| Thermal | `pmset -g therm`: no warning level EVER recorded |
| Memory / swap | 44% free; swap flat at 541.75 MB across all 600 samples |
| Shader compilation | cache static at 1.1 MB, newest real write the previous day |
| msync / wineserver | 7-8% — the healthy figure (the broken case is ~40%) |
| Time Machine | `tmutil status` → `Running = 0` |
| GPU saturation | 80% avg in-match, 89% peak — loaded but never pegged |
| Cloudflare WARP VPN | 38.7ms ± 5ms over 10 packets — stable |

## Load profile (useful baseline for this title)
```
menu/lobby :  ASBR  88%  GPU 50%

```

## Lessons
- **A 4-packet ping is not a measurement.** The first sample read as jittery
  (stddev 17ms) purely from one outlier; 10 packets showed 38.7ms ± 5ms. It nearly
  sent the investigation into the VPN for no reason.
- **Check what the audio device is.** `system_profiler SPAudioDataType | grep -A4
  "Default Output Device"` — a `Transport: AirPlay` line explains "lag" that no
  CPU/GPU/thermal metric can account for.
- The giveaway was the shape of the data: *nothing was saturated*. When every local
  metric is healthy and it still feels bad, the problem is outside the machine.
